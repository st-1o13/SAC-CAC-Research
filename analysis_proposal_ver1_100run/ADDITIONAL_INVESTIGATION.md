## 1. 制約違反の定義確認

### 事実（コード：`train.py` 329-332行目、`agent.py` 84-90行目）

```python
# agent.py
def h(self, x):
    thdot = x[:, 2]
    h_raw = thdot + 2.0
    h_pos_clipped = torch.clamp(h_raw, max=2.0)
    h_norm = h_pos_clipped / 2.0
    return h_norm

# train.py（環境ステップ実行後）
if agent.h(next_state_t.unsqueeze(0)).item() < 0.0:
    violations += 1
```

- **違反判定の条件式**：行動実行後の次状態`next_state`に対する正規化済み安全指標`h(next_state) < 0.0`。生の角速度`h_raw`や`h_value`（移動平均）ではなく、**都度計算される`h()`の値**を使用。
- **カウント方法**：条件を満たすたびに整数カウンタ`violations`を+1するだけの**単純な二値判定・回数カウント**。違反の深さ（`h`がどれだけ0を下回ったか）は一切反映されない。
- **1エピソードあたりの集計**：`episode_violations.append(violations)`（`train.py:356`）。エピソード内で発生した違反回数の**単純合計**であり、エピソード長（ステップ数）による正規化は行われていない。
- **学習中と評価時の違い**：`config.py`の`args`に`eval_interval: 10`というキーが定義されているが、`train.py`・`agent.py`のいずれにも`eval_interval`を参照する箇所は存在しない（grep確認済み、ヒットなし）。**現在のコードには学習中とは別の評価専用フェーズは実装されていない。** `agent.select_action(state, evaluate=False)`がデフォルト（`evaluate`引数を渡していない）で全ステップ呼ばれており、`SoftActorNet.sample()`が返す**確率的サンプル行動**（`rsample()`、探索ノイズを含む）が常に使われている。決定論的な平均行動（`evaluate=True`）が使われる箇所はコード上どこにもない。
- **違反の程度を評価できる指標**：`h`の深さ（負の大きさ）、違反の連続時間、違反1回あたりの重大度を示す指標は保存されていない。`episode_h`（エピソード内平均）はあるが、これは違反時のみの平均ではなく全ステップの平均であり、違反の重大度指標としては使えない。

### 検討：現在の違反回数だけで安全性を十分に評価できるか（推測を含む考察）

以下の理由から、**現在の「違反回数」単独では安全性の評価として不十分である可能性が高い**：

1. 二値判定のため、「`h`が-0.01であるステップ」と「`h`が-2.5であるステップ」が同じ1回としてカウントされ、**危険の深刻度が区別できない**（事実：コード上、重大度は一切記録されない）。
2. エピソード長で正規化されていないため、仮にエピソード長が変動する場合（Pendulum-v1は通常200ステップで打ち切りのみのため大きくは変動しないと考えられるが、実際のエピソード長は保存されておらず本分析では確認できない）比較の公平性に疑問が残る（推測：影響は小さい可能性が高いが未確認）。
3. 学習中の**確率的行動**でカウントされているため、方策が収束した後に決定論的行動で評価した場合の違反率とは**異なる可能性がある**（推測：探索ノイズが違反率を実際より高く見せている可能性があるが、逆に方策自体が危険な決定論的行動を学習している可能性も否定できず、現状のデータからは切り分けられない）。

### `episode_h`平均が正、`episode_h_value`平均が負になる理由の調査

**確認できた事実**：
1. `episode_h`は**現在のロールアウト状態**（環境から得た実際の状態、現在の方策で生成）に対する`h()`の**単純平均**。
2. `episode_h_value`は**リプレイバッファから一様ランダムサンプリングしたミニバッチ**に対する`h()`の**下位15%分位点**を、直近最大80回分**移動平均**したもの。
3. `config.py`の`args`より、`memory_size=100000`、`start_steps=1000`、`batch_size=256`。Pendulum-v1の`max_episode_steps=200`（環境仕様として確認済み）であり、`total_episodes=250`のため、**1 runあたりの最大環境ステップ数は250×200=50,000で、`memory_size`(100,000)を下回る**。したがって**1 run内でリプレイバッファが一度も一杯にならず、古い遷移（学習初期・ランダム行動期を含む）が削除されずに run終了までバッファ内に残り続ける**（事実：パラメータ値から導出）。
4. `random.sample()`（`replay_memory.py`）は**バッファ全体から一様ランダムに**ミニバッチを抽出する。優先度付きサンプリングや直近重視の仕組みはない（事実：コード確認済み）。

**疑われる原因（推測、複数要因が複合している可能性）**：
- `episode_h`は「今の（改善されつつある）方策」が生成した状態のみを見るのに対し、`episode_h_value`は「学習初期の未熟な方策・ランダム行動期を含む古い遷移」が今も一様な確率で混入し得るバッファからサンプルするため、**`episode_h_value`の方が構造的に低く（悪く）出やすい**。
- さらに`h_value`は平均ではなく**下位15%分位点**（悲観的な統計量）を採用しているため、バッチ内の一部の悪い遷移に強く引きずられやすい。
- 上記2つの要因（①サンプル元の違い＝現在の方策 vs バッファ全体、②統計量の違い＝平均 vs 下位15%分位点）が組み合わさることで、`episode_h`（正）と`episode_h_value`（負）の符号が逆転する現象を**論理的には説明できる**。

**現時点では判断できないこと**：
- 上記2つの要因（サンプル元の違い、統計量の違い）のうち、どちらが符号逆転への寄与が大きいかは、**両方を分離した追加検証（例：バッファ全体に対する単純平均を別途ログする等）なしには定量的に切り分けられない**。
- リプレイバッファ内で「古い（学習初期の）遷移」が実際にどの程度の割合でミニバッチに含まれ続けているかは、遷移ごとの生成episode番号を記録していない現状のコードでは**直接確認できない**。

## 3. m_dir異常値の追加調査

### m_dirの計算式（事実：`gradient_blend.py` `restricted_direction()`）

```python
dot12 = torch.dot(W1, W2_use)        # W1=安全勾配, W2_use=shrink後の性能勾配
w1_sq = (norm1 ** 2).clamp(min=eps)  # eps = 1e-8
w2_sq = (norm2 ** 2).clamp(min=eps)

denom1 = dot12 - w1_sq
denom1_safe = where(|denom1| < eps, sign(denom1)*eps + eps, denom1)
m1 = dot12 / denom1_safe

denom2 = w2_sq - dot12
denom2_safe = where(|denom2| < eps, sign(denom2)*eps + eps, denom2)
m2 = w2_sq / denom2_safe

m_progress = m2 * (1 - t) + m1 * t          # t = progress（0〜1）
safety_level = sigmoid(k * (c - h_value))    # k=1.63, c=0.55
m_dir = safety_level * m1 + (1 - safety_level) * m_progress
m_dir = clamp(m_dir, min(m1, m2), max(m1, m2))   # ← 最終的にm1・m2の範囲内にクランプされる
```

- 保存されている`episode_m_dir`は、このクランプ後の**スカラーm_dirを、そのエピソード内の全update呼び出しについて平均した値**（`train.py:360`, `episode_m_dir.append(mean(perupdate_m_dir))`）。

| 数値的不安定性が疑われる条件 | ○（理論的に） | 下記参照 |

### 数値的不安定性が疑われる条件（推測、コードの数式から導出）

`denom1_safe`/`denom2_safe`の保護ロジックは、**分母の絶対値が`eps=1e-8`未満の場合のみ**発動する。しかし、分母が例えば`1e-4`程度まで小さくなった場合（`eps`の保護は発動しない）、`dot12`がO(1)〜O(10)程度でも`m1 = dot12 / 1e-4`は**容易に1万〜10万のオーダーに達し得る**。つまり：

- `dot12 ≈ w1_sq`（安全勾配とshrink後性能勾配の内積が、安全勾配自身のノルム二乗に近い）→ `denom1`がほぼゼロ → `m1`が発散
- `w2_sq ≈ dot12`（shrink後性能勾配のノルム二乗が内積に近い）→ `denom2`がほぼゼロ → `m2`が発散

このような「ほぼゼロだが完全にゼロではない分母」による発散は、**`eps`保護が「完全なゼロ割り」しか想定しておらず、「ほぼゼロ」のケースを防げていない設計上の弱点**によって説明可能である（推測：コードの数式構造から論理的に導かれるが、実際にどちらの分母が原因だったかは`dot12`/`w1_sq`/`w2_sq`が保存されていないため**本分析では直接確認できない**）。

### 該当エピソード周辺の実測データ（事実：既存npzの再集計）

`m_dir`の3件の極端値（run_id=54,episode=182／run_id=83,episode=65／run_id=60,episode=246）について前後2エピソードを確認したところ、**いずれも前後のエピソードのm_dirは0.4〜1.3程度の通常範囲であり、単一エピソードだけの孤立したスパイクである**。さらに重要な点として、これら3件では**同じエピソードの`episode_grad_dot`（生の内積）は特に異常な値を示していない**（例：run 54 ep182では-4.88、run 83 ep65では-5.36、run 60 ep246では0.59——いずれも他エピソードと同程度）。

**これは事実として確認できる**：m_dirの異常な発散は、内積`dot12`自体の絶対値が大きいことによるものではなく、**分母（`denom1`または`denom2`）がたまたま極端に小さくなった「ほぼゼロ割り」に起因する可能性が高いことと整合する**（推測だが、上記の理論的説明と実測パターンが一致している）。

一方、`grad_dot`側の極端な負の外れ値（run_id=3,7,55等）を調べたところ、こちらは異なるパターンを示した：該当エピソードでは**`episode_stability_grad`（W2ノルム、平常時6〜7 → 該当エピソードで24〜39と3〜5倍）、`episode_h_value`（-1.7〜-1.9という深く負の値）、`episode_violations`（近傍エピソードで78〜141回という高い違反数）が同時に観測されている**（事実：npz再集計により確認）。

**疑われる原因（推測）**：`grad_dot`の極端値は、安全性が大きく悪化している局面（h_valueが深く負、違反多発）で、Actorの勾配（特に性能側`grad_st`のノルム）自体が大きくなり、その結果として生の内積（クリップ前）も大きな値を取ることで発生している可能性が高い。これは`m_dir`の発散（分母の偶発的な近ゼロ化）とは**異なるメカニズム**である可能性が示唆される。

## 5. 最終報告

### 5.1 確認できた事実

1. 違反判定は`h(next_state) < 0.0`の二値条件であり、重大度を反映しない単純カウント。エピソード長による正規化もない。
2. 現在のコードには学習中とは別の評価専用フェーズが実装されていない（`eval_interval`は定義されているが未使用）。全結果は確率的行動（探索ノイズ込み）によるもの。
3. `episode_h`は現在の方策によるライブロールアウト状態の単純平均、`episode_h_value`はリプレイバッファから一様サンプルしたミニバッチの下位15%分位点を80回移動平均したもの——**参照するデータ源も統計量も異なる**。
4. `memory_size(100,000) > 1runの最大環境ステップ数(50,000)`のため、1 run内でバッファは一度も一杯にならず、古い（学習初期の）遷移が最後まで残り続ける。
5. `m_dir`は数式上`clamp(min(m1,m2), max(m1,m2))`されるため、その異常値は必ずm1またはm2自体の異常な発散に由来する。
6. `m_dir`の3件の極端値は、いずれも前後エピソードと比較して孤立した単発スパイクであり、`grad_dot`は同エピソードで異常を示さない。
7. `grad_dot`の8件の極端な負の外れ値は、`episode_stability_grad`の急上昇（3〜5倍）・`episode_h_value`の著しい悪化・近傍エピソードでの違反急増と同時に観測される。
8. `dot12`, `m1`, `m2`, `denom1`, `denom2`, `sa_norm_raw`（W1ノルム）はいずれも現在のnpzファイルに保存されておらず、既存データからの直接確認はできない。

### 5.2 疑われる原因

1. `episode_h`と`episode_h_value`の符号逆転：サンプル元（現在の方策 vs リプレイバッファ全体）と統計量（平均 vs 下位15%分位点）の違いが複合した結果と考えられる。
2. `m_dir`の異常値：`denom1_safe`/`denom2_safe`の保護が「完全なゼロ割り」しか防げず、「ほぼゼロ」の分母による発散を防げていない設計上の弱点による可能性が高い。
