## 1. CAC Stage2の制約付き最適化問題の定式化（原論文の式に基づく）

### 1.1 報酬関数（原文引用・確認済み）

**安全報酬**（Eq.7、Theorem 1証明中の記述と突き合わせて確認。抽出結果の一部に無関係な文字混入があったため、証明部分の再掲"`r1 = min(h(st+1)+(α0-1)h(st),0)`"と照合し復元）：

> `r1(st,at) = min(h(st+1) + (α0-1)h(st), 0)`　（Eq.7、`r1≤0`）

有限長エピソードでの早期終了を防ぐための正規化版（Eq.12、原文引用）：

> `r1(st,at) = exp(min(h(st+1) + (α0-1)h(st), 0))`　（Eq.12、"obviously r1∈(0,1]"と明記）

**性能（ナビゲーション）報酬**（Eq.9、原文引用。CAC論文自身が「任意の適切な報酬関数を設定してよい、例えば」と前置きした**一例**であり必須ではない）：

> `r2(st,at) = -max(l(st+1) + (β0-1)l(st), 0)`

ここで`l(s):Rⁿ→R`は**制御Lyapunov関数（CLF）**であり、`β0`はその期待減衰率。

### 1.2 Restricted Policy Update（Eq.10、原文引用）

> `∇θ = argmax_e  e·∇J2(θ)`
> `s.t.  e·∇J1(θ) ≥ 0`
> `      [第3行：記号消失につき次項で扱う]`

`∇J1(θ)`, `∇J2(θ)`はそれぞれ報酬`r1`, `r2`によるActor損失関数`J1(θ)`, `J2(θ)`の勾配（原文："`J1(θ),J2(θ)` are actor loss functions with reward `r1,r2` respectively, and `∇` is gradient operator"）。

**第3行の記号消失について**：layoutモード抽出では`e  J2()`、非layoutモード抽出でも同様に`e ≤ ∥∇J2(θ)∥`に相当すると見られる記号（ノルム記号・不等号）が失われた`e  J2()`という文字列のみが確認できた。この文字列は「`‖e‖ ≤ ‖∇J2(θ)‖`」（更新方向`e`のノルムを性能勾配のノルムで上限を定める制約）である可能性が高いと考えられるが、**記号が完全に失われているため、これは推定復元であり、原論文の当該箇所を画像として直接確認できていない現時点では断定できない**。以降、この制約を「（推定）ノルム制約」と呼び、事実として確定した制約とは区別して扱う。

### 1.3 制約の実務的強化（第IV.B節「Gradient enhancement」、原文引用）

> "it is essential to enhance the constraint as `e·∇J1(θ) ≥ ε` or `cos{e,∇J1(θ)} ≥ ε`, `ε>0`"

理由として原文は2点を挙げる：①ステップ幅が有限であり局所勾配が大域収束を保証しないこと、②真の`∇J1(θ)`は未知でありデータからの推定`∇̂J1(θ)`で代用されること。**この強化は境界`≥0`を`≥ε`（正のマージン）へ厳しくするものであり、ノルム制約を追加・変更するものではない**。

### 1.4 Algorithm 1の構造（原文引用に基づく再構成）

```
Stage 1（5〜8行目）：r1のみでActorとCritic(Q1/V1)を更新するループ
  θ ← θ - η∇J1(θ)
  θ1 ← θ1 - η1∇θ1 L1(θ1)

Stage 2（12〜17行目）：
  e ← (Eq.10で計算)
  θ ← θ - ηe
  θ1 ← θ1 - η1∇θ1 L1(θ1)   # 安全Criticも毎ステップ更新継続
  θ2 ← θ2 - η2∇θ2 L2(θ2)   # 性能Criticを更新
```

**重要な事実**：Algorithm 1は13行目で単に「`e ← (10)`」と記すのみであり、**Eq.10をどのような計算手続き（数値ソルバー・閉形式解等）で解くかについて、本文中に具体的な記述は確認できなかった**。したがって、「CACは凸最適化ソルバーを用いる」という記述は、本レポート作成時点の原文確認の範囲では**確認できた事実ではなく、Eq.10の問題構造（線形目的関数・線形不等式制約）から推測される一般的な性質にとどまる**。

### 1.5 安全性保証（Theorem 1、原文引用に基づく整理）

Theorem 1は、初期状態`s0`における安全Critic値`V1(s0)=0`（または有限エピソード長`kmax`を考慮したバイアス項`(1-α0^kmax)/(1-α0)`との一致）が成り立てば、系が安全集合`C`に留まり続けることを述べる。**この保証は、Stage1で安全Criticが十分に学習され`V1(s0)≈0`に達していることを前提とする**。

## 2. CACの制約付き最適化に登場する変数・勾配・制約条件の意味

| 記号 | 意味 | Ver.1コード上の対応（第3節で詳述） |
|---|---|---|
| `h(s)` | 離散時間CBF（Definition 2、Eq.4の前方不変性条件を満たす関数） | `agent.py`の`h()`（Pendulum角速度由来） |
| `l(s)` | 制御Lyapunov関数（CLF）、Eq.9の性能報酬に使用 | **Ver.1には対応するものが存在しない**（後述） |
| `J1(θ)` | 安全報酬`r1`によるActor損失 | `safety_loss`（`critic_safe`のQ値由来） |
| `J2(θ)` | 性能報酬`r2`によるActor損失 | `stability_loss`（`critic_net`のQ値由来） |
| `∇J1(θ)` | 安全性勾配 | `grad_sa`（`W1`として`restricted_direction`へ渡される） |
| `∇J2(θ)` | 性能勾配 | `grad_st`（`W2`として`restricted_direction`へ渡される） |
| `e` | 制約付き最適化の解（更新方向） | `restricted_direction()`の戻り値`e`（**同じ変数名`e`が使われているが、両者が同一の数学的対象であることは未証明**） |
| `e·∇J1(θ)≥0` | 安全性を後退させないという制約 | Ver.1では対応する**明示的な制約充足の保証機構が存在しない**（第5節で詳述） |
| （推定）`‖e‖≤‖∇J2(θ)‖` | 更新方向の大きさを性能勾配のスケールに合わせる制約 | Ver.1では`m_soft`/`rel_cap`/`±21`/`400`/`102.5`/`50`という**全く別の多段階クリップ機構**に置き換わっている |

**重要な確認事実**：CACのEq.9（性能報酬）は制御Lyapunov関数`l(s)`に基づく設計例であり、これは真正のLyapunov安定性に関わる量である。一方、Ver.1は環境（Pendulum-v1）が返す標準報酬をそのまま性能報酬として使用しており（既存調査で確認済み）、Eq.9のCLFベース報酬を採用していない。したがって、**Ver.1のコード変数名`stability_loss`は、CAC自身が持つ真正のLyapunov的な性能報酬設計（Eq.9）とも、一般的なLyapunov安定性の概念とも対応しない**——これは`CBF_GRADIENT_LITERATURE_REVIEW.md`で指摘したBLAC論文との用語混同リスクに加え、**CAC自身との対応においても同様の混同リスクがあることを新たに確認した**。

## 3. Proposal Ver.1の処理のコードからの正確な抽出

`gradient_blend.py`の`restricted_direction(W1, W2, progress, h_value, ...)`（引数は`agent.py`から`restricted_direction(grad_sa, grad_st, progress=progress, h_value=h_value)`として呼ばれる。すなわち`W1=grad_sa`＝安全性勾配、`W2=grad_st`＝性能勾配）：

```
W2_use = W2 * shrink                         # shrink = 1/(1+log10(‖W2‖+1))  ※CACには対応する処理なし
dot12  = W1・W2_use
denom1 = dot12 - ‖W1‖²  ;  m1 = dot12/denom1
denom2 = ‖W2‖² - dot12  ;  m2 = ‖W2‖²/denom2
t = clip(progress,0,1)  ;  m_progress = (1-t)m2 + t・m1
safety_level = sigmoid(k(c - h_value))        # k=1.63, c=0.55
m_dir = safety_level・m1 + (1-safety_level)・m_progress
m_dir = clip(m_dir, min(m1,m2), max(m1,m2))
w_dir = m_dir・W1 + (1-m_dir)・W2_use
m0 = (W2_use・w_dir) / ‖w_dir‖²
m_soft = sign(m0)・|m0|/(1+(|m0|/100)^1.5)     # m_thresh=100, p=1.5
rel_cap = 4.5・(‖W2_use‖+ε)
m_rel = sign(m_soft)・min(|m_soft|, rel_cap)
m_scale = clip(m_rel, -21, 21)
w_scaled = m_scale・w_dir
e = w_scaled  （‖w_scaled‖>400 なら 400 にスケールダウン）
```

`agent.py`側でのその後の処理（`e`を受け取った後）：

```
if ‖e‖>102.5:  e = e・(102.5/‖e‖)     # agent.py独自の追加クリップ
p.grad = e を各パラメータへ分解して代入
torch.nn.utils.clip_grad_norm_(actor_net, 50.0)   # Actor全体の最終クリップ
actor_optim.step()
```

`grad_dot`（`episode_grad_dot`として保存される値）は、`restricted_direction`内部の`dot12`（shrink後の`W2_use`との内積）とは**別の量**であり、`agent.py`内で`dot = torch.dot(grad_st, grad_sa).item()`として**shrink前の生の`W1`・`W2`の内積**として計算される（`STAGE_B_EXTENDED_REPORT.md`で確認済み）。

| 観点 | CAC（Eq.10） | Proposal Ver.1 |
|---|---|---|

| 非線形処理の有無 | 記述なし（線形計画として定式化） | `log10`shrink、`m_soft`のべき乗型ソフト閾値、`sign`・`min`・`clamp`による多段階の非線形処理が明示的に存在する |
| 計算処理の構造 | 制約付き最適化問題（解法不明） | 決定的な閉形式の代数式の連鎖（`torch`のテンソル演算のみ、ソルバー呼び出しなし） |

## 5. m1・m2はCACの最適解そのものか、特定の条件から導出される係数か

### 5.1 m1について（事実と推測を分離）

**事実（代数的に確認済み）**：`m1`は`e·W1=0`という**等式**条件を満たす、`W1`と`W2_use`のアフィン結合の係数である。これは`LITERATURE_AND_MATHEMATICAL_COMPARISON.md`第4.2節で導出した恒等式`e=(1-m1)・[W2_use-(dot(W1,W2_use)/‖W1‖²)W1]`（標準的な直交射影と比例関係にある）と整合する。

**推測（未証明）**：CACのEq.10は`e·∇J1(θ)≥0`という**不等式**制約であり、`m1`が満たす`e·W1=0`は、この不等式制約が**境界で有効（active）な場合**の解に対応する可能性がある——線形関数`e·∇J2(θ)`を、半空間`e·∇J1(θ)≥0`とノルム制約の交わりの上で最大化する場合、無制約の最大化方向（`∇J2(θ)`そのもの）が半空間の外にあれば、真の最適解は制約境界`e·∇J1(θ)=0`上でノルム制約と両立する点になる、という一般的な線形計画の性質に基づく推測である。**しかし、この推測は（a）Eq.10第3行の（推定）ノルム制約の内容が確定していないこと、（b）`m1`が`W2_use`（shrink後）を用いており、CACのEq.10には存在しないshrink処理を経ていること、の2点により証明されたものではない。**

**明示的な非断定**：**`m1`がCACの制約付き最適化問題全体（両方の制約を考慮した）の厳密解であるとは断定しない。** 上記はあくまで、制約が境界で有効な場合に限定した、部分的な対応関係の可能性を示す推測である。

### 5.2 m2について（事実と推測を分離）

**事実**：`m2=‖W2‖²/(‖W2‖²-dot12)`という代数式である。過去の調査（`ADDITIONAL_INVESTIGATION.md`系列）で「厳密解ではなく近似的な式」と位置づけられているが、**何を近似しているのかの代数的な導出根拠は、本レポート作成時点でも確認できていない**。

**推測（未証明）**：`m2`は「`e·W2_use=0`（性能方向への直交条件）に近い性質を持たせることを意図した式」である可能性があるが、`m1`のケースのような恒等式による裏付けは確認できていない。`m2`とPCRPOの`gc+`との対応も、`LITERATURE_AND_MATHEMATICAL_COMPARISON.md`で繰り返し「未検証」と記載された通り、本レポートでも確認できていない。

### 5.3 CACの安全制約`e·∇J1(θ)≥0`とVer.1の`e·W1`の関係（新たに確認した事実）

本レポート作成にあたり、`m2`が支配的な場合（`m_dir=m2`）に`e·W1`がどのような符号を持つかを代数的に検証した。

`e=m2・W1+(1-m2)・W2_use`とし、`e・W1 = m2・w1_sq+(1-m2)・dot12`を整理すると、

`e・W1 = (w1_sq・w2_sq - dot12²) / denom2`

という式が得られる（本レポート作成にあたり新たに導出。分子`w1_sq・w2_sq-dot12²`はコーシー・シュワルツの不等式により常に`≥0`である）。したがって、

**`e・W1`（`m2`使用時）の符号 = `denom2`の符号 = `sign(‖W2_use‖²-dot12)`**

が成り立つ。すなわち、`‖W2_use‖²<dot12`（安全性勾配と性能勾配の内積が、性能勾配自身のノルムの2乗より大きい場合）には、`m2`方向の更新は`e・W1<0`となり、**CACの安全制約`e·∇J1(θ)≥0`を満たさない**。

**この事実は、Ver.1が`m2`寄りにブレンドされる局面（`safety_level`が低い、すなわち安全度が高いと判定された局面）において、CACが要求する安全制約を数学的に保証していないことを意味する**（推測ではなく、上記の代数的導出による事実）。ただし、実際の学習データにおいてこの符号がどの程度の頻度で負になるかは、既存の診断データ（`episode_grad_dot`は`shrink`前の生の内積であり、上記の`dot12`＝shrink後の内積とは異なる値である点に注意）を用いた追加の再解析が必要であり、本レポートでは実施していない。

## 6. Ver.1の勾配調整はCAC Stage2の最適化をどの範囲で近似・代替していると解釈できるか（証明済みとして扱わない）

以下はいずれも**解釈上の仮説**であり、証明されたものではない。

1. **仮説**：Ver.1は、CACのEq.10が要求する「安全制約を満たす中での性能最大化」という枠組みを、単一の制約付き最適化問題として毎ステップ解く代わりに、あらかじめ計算可能な2つの候補方向（`m1`：安全境界上の方向、`m2`：性能寄りの方向）を`safety_level`という連続的な指標で混合することにより、**質的に近い振る舞いを低い計算コストで再現しようとする設計**として解釈できる可能性がある。
2. **仮説に対する反証材料（第5.3節の事実）**：しかし、`m2`が支配的な局面では、CACの中核制約`e·∇J1(θ)≥0`が代数的に保証されないことが確認された。したがって、**Ver.1はCACの制約付き最適化を「近似」しているというよりも、「一部の局面では異なる制約充足特性を持つ、別の設計に置き換えている」と解釈する方がより正確である可能性がある**。
3. **Stage1撤廃との関係**：CACのTheorem 1による安全性保証は、Stage1で安全Criticが収束していること（`V1(s0)≈0`）を前提とする。Ver.1は`stage1_episodes=0`によりStage1を実行しないため、**Theorem 1の前提条件がそもそも満たされておらず、Ver.1がCACと同等の安全性保証を持つと解釈することはできない**（これは仮説ではなく、Theorem 1の前提条件とVer.1の設定を直接突き合わせた事実に基づく結論）。
4. **計算コストの観点**：Ver.1が反復を伴わない代数演算のみで完結すること（第4節）は事実として確認できるが、これが「CACの計算コストを削減した」と主張するには、CAC側が実際にどのような計算手続きでEq.10を解いているかが原論文からは確認できない（第1.4節）ため、**比較対象となるCAC側の計算コストの実態そのものが未確定**であり、この点についても断定は避ける。
