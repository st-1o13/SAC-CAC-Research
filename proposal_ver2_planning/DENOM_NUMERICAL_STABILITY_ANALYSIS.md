# denom1_safe / denom2_safe の数値安定性問題に関する追加調査

**本レポートは分析・追加調査のみを目的とする。既存レポートは一切変更していない。研究コードは一切変更せず、新しい実験も実行していない。Git操作も行っていない。**

前回の検証（`M1_M2_CAC_OPTIMALITY_VERIFICATION.md`第4.2節）で発見した「`denom1`/`denom2`が開区間`(-eps,0)`にあるとき`denom_safe`が厳密に0になる」という問題について、実装・数学・研究上の扱いの3観点から追加調査した。**本調査の過程で、前回レポートの記述を訂正する必要がある、より重要な事実（フォールバックが実際には正常に機能しない可能性）を新たに発見した。この点は本レポートで明確に訂正として扱う。**

---

## 1. 実装の確認

### 1.1 denom1_safe / denom2_safeの正確な計算式（`gradient_blend.py`、無変更のコードを再確認）

```python
denom1 = dot12 - w1_sq
denom1_safe = torch.where(torch.abs(denom1) < eps, torch.sign(denom1) * eps + eps, denom1)
m1 = dot12 / denom1_safe

denom2 = w2_sq - dot12
denom2_safe = torch.where(torch.abs(denom2) < eps, torch.sign(denom2) * eps + eps, denom2)
m2 = w2_sq / denom2_safe
```

`eps`のデフォルト値は`1e-8`（関数シグネチャ`eps: float = 1e-8`）。

### 1.2 denomが正・負・0の場合の挙動（実際に数値実行して確認済み、前回レポートと同じ検証を再掲）

| `denom`の値 | `sign(denom)` | `denom_safe`の値 | 備考 |
|---|---|---|---|
| `0.0`（ちょうど0） | `0` | `eps`（`=1e-8`、正の小さい値） | 安全に機能する |
| 正の小さい値（`0<denom<eps`） | `+1` | `2eps`（`=2e-8`、正の小さい値） | 安全に機能する |
| **負の小さい値（`-eps<denom<0`）** | `-1` | **`0.0`（厳密にゼロ）** | **安全に機能しない**（前回レポートで発見） |
| `|denom|≥eps`（十分大きい） | — | `denom`そのまま | 代入は発動しない |

**確認方法**：`torch.where`・`torch.sign`を実際に数値実行し、`denom1=-1e-10`のとき`denom1_safe=0.0`となることを確認済み（前回レポート、本レポート共通）。

### 1.3 isfiniteチェックとフォールバックの動作——訂正が必要な発見

`gradient_blend.py`の該当箇所（`m1`,`m2`が計算された後、`w_dir`計算直後）：

```python
w_dir = m_dir * W1 + (1.0 - m_dir) * W2_use
if w_dir.norm() < eps or not torch.isfinite(w_dir).all():
    return W2_use.clone()
```

**前回レポート（`M1_M2_CAC_OPTIMALITY_VERIFICATION.md`）では、この分岐が`W2_use.clone()`という「フォールバック値」に安全に切り替わると記述したが、これは不完全な確認であったことが、今回の追加調査で判明した。**

`restricted_direction()`関数の正常時の戻り値は`return torch.nan_to_num(w_scaled, nan=0.0), float(m_dir)`という**タプル（2要素）**である。しかし、上記の早期リターン文（および同関数内の他の早期リターン文、`return torch.zeros_like(W1)`、`return W2.clone()`、`return W1.clone()`）は**いずれも単一のテンソルのみを返しており、タプルではない**。

`agent.py`側の呼び出しは`e, m_dir = restricted_direction(grad_sa, grad_st, progress=progress, h_value=h_value)`という、**戻り値を2つの変数にアンパックする形**になっている。

**実際に検証した結果**：単一のテンソル（Actor全体のパラメータ数に相当する`67,330`要素、`SoftActorNet(hidden_size=256)`で実際に確認済み）を`e, m_dir = <tensor>`という形でアンパックしようとすると、**`ValueError: too many values to unpack (expected 2)`という例外が発生し、プログラムがクラッシュすることを直接確認した**。

**したがって、`denom1`または`denom2`が`(-eps,0)`区間に入り`m1`または`m2`が`±inf`になった場合、`w_dir`が非有限になって早期リターン文に到達すると、意図された「安全なフォールバック」ではなく、実際には`agent.py`側でPythonの例外が送出され、学習プロセスがクラッシュする可能性が高い。**

### 1.4 m1/m2/m_dirへの影響（連鎖の整理）

1. `denom1`（または`denom2`）が`(-eps,0)`に入る → `denom_safe=0` → `m1`（または`m2`）`=±inf`
2. `m_progress=(1-t)m2+t・m1`、`m_dir=σ・m1+(1-σ)・m_progress`：`inf`を含む線形結合は、係数が厳密に0でない限り`inf`または`nan`になる
3. `w_dir=m_dir・W1+(1-m_dir)・W2_use`：`m_dir`が`inf`/`nan`であれば、`W1`,`W2_use`の対応する成分が厳密に0でない限り`w_dir`も非有限になる
4. `torch.isfinite(w_dir).all()`が`False`となり、早期リターン文に到達
5. **単一テンソルを2変数にアンパックしようとして例外が発生する（新たに確認した事実）**

## 2. 数学的な整理

### 2.1 denomが(-eps,0)に入る条件

`denom1=c-a`（`c=dot12=W1・W2_use`, `a=‖W1‖²`）について、`denom1∈(-eps,0)`となるのは`c`が`a`よりわずかに小さい場合、すなわち`0<a-c<eps`のときである。`denom2=B-c`（`B=‖W2‖²`）についても同様に`0<c-B<eps`のとき`denom2∈(-eps,0)`となる。

いずれも、**2つの独立に変動する量（内積と、ノルムの2乗）が偶然にきわめて近い値を取る、測度論的には「稀」な状況**であるが、学習が進行する中で`W1`,`W2`の関係が特定のパターンに収束する場合には、発生しうる。

### 2.2 m1/m2が±infになる条件

`m1=c/denom1_safe`について、`denom1_safe=0`となるのは`denom1∈(-eps,0)`のときのみ（`denom1=0`ちょうどの場合は`denom1_safe=eps≠0`となるため除外される）。このとき`m1=c/0`となり、`c≠0`であれば`±inf`（符号は`c`の符号に一致）。**`c=0`かつ`denom1∈(-eps,0)`という組み合わせは、`denom1=c-a=-a`となり`a∈(0,eps)`を要求するため、理論上は可能だが`‖W1‖²`が`eps=1e-8`未満というきわめて小さいノルムを要求する、さらに稀な状況である。**

### 2.3 フォールバック後の方向ベクトルがどのように定義されるか

**第1.3節の発見により、この問いへの答えは修正が必要である**：

- **意図された動作（コードのコメント・変数名から推測される設計意図）**：`W2_use.clone()`という、`W1`成分を一切含まない、shrink後の性能勾配のみを返す。
- **実際に起こりうる動作（本レポートで確認した事実）**：`agent.py`の呼び出し規約（`e, m_dir = restricted_direction(...)`）と、早期リターン文の戻り値の型が一致していないため、**単一テンソルの戻り値が2変数へのアンパックに失敗し、`ValueError`例外が送出される可能性が高い**。

### 2.4 CAC最適方向との数学的対応が維持されるか

**この問いも、前提が崩れるため再整理が必要である**。仮に（本来の設計意図通り）`W2_use.clone()`が実際に返され、`agent.py`側で正常に受け取られたと仮定した場合：

- `W2_use`は、`CAC_VER1_MATHEMATICAL_COMPARISON.md`・`M1_M2_CAC_OPTIMALITY_ANALYSIS.md`で確認した通り、**CACの真の最適解のいずれの領域とも一致しない**。特に、この不安定性が発生する`denom1∈(-eps,0)`という条件は`c=dot12≈a>0`に近い状況（`c`が正でほぼ`a`に等しい）を意味し、`sign(c)=sign(D)`（`D`は生の内積）であるから、**多くの場合`D>0`（非対立、CACの真の解は`e*=W2`）の近傍で発生すると考えられる**（ただし`c≈a>0`は`D>0`を強く示唆するが、`s`の値次第で境界的なケースもありうるため、この対応関係は「未確認」として扱う）。この場合、`W2_use`（shrink後）は`CAC`が要求する`e*=W2`（生の値）に近いが、shrinkの分だけ乖離する。
- **したがって、フォールバックが実際に機能した場合でも、CAC最適解との対応は「近いが一致しない」程度であり、正確な対応関係の証明はできていない。**
- **さらに重要な点として、第1.3節で確認した通り、フォールバック自体が正常に機能しない可能性が高いため、この対応関係の議論は実践上の意味を持たない可能性がある。**

## 3. 研究上の扱い

### 3.1 現状の実装で発生し得る問題

1. `denom1`または`denom2`が`(-eps,0)`に入ると、`m1`または`m2`が`±inf`になる（コードの数式から確認できる事実）。
2. この`±inf`が`w_dir`まで伝播すると、`torch.isfinite`チェックに引っかかり、早期リターン文に到達する（確認済みの事実）。
3. **この早期リターン文の戻り値の型（単一テンソル）が、正常時の戻り値の型（タプル）と一致しておらず、呼び出し元でのアンパックが失敗し、`ValueError`例外が送出される可能性が高い（本レポートで新たに確認した事実）。**

### 3.2 実験結果から確認できる事実

- Proposal Ver.1の100-run本番実験（`runs_proposal_ver1/`）、および`Stage B`・`Stage B-extended`で実施した追加診断run（合計6 run）は、**いずれも正常終了（exit code 0）しており、途中でクラッシュした形跡はない**（既存の実行ログで確認済み）。
- **これは、上記の問題（`denom1`/`denom2`が`(-eps,0)`に入り、かつそれが`w_dir`まで伝播する事態）が、これまでに実施された全ての実測（合計106 run：100-run本番＋Stage B 5run＋Stage B-extended検証n=1）において、一度も発生していないことを強く示唆する。**
- `STAGE_B_EXTENDED_REPORT.md`で報告された`m1`/`m2`の発散事例（例：`m1≈76,642,016`）は、いずれも**有限の大きな値**であり、`±inf`ではなかった（`denom1=0.0`ちょうど、または`denom1`が正の小さい値等、`denom_safe`が正の有限値になるケースだったと考えられる）。

### 3.3 現時点では未確認の影響

1. `denom1`または`denom2`が実際に`(-eps,0)`という狭い区間に入った事例が、今回調査した106 run以外（より長期の学習、異なるseed、異なる環境等）で発生する可能性。
2. 万が一この分岐が実際にトリガーされた場合に、`agent.py`側で本当に`ValueError`が送出されるか（本レポートは`restricted_direction()`単体の戻り値の型を独立に検証したものであり、`agent.py`の呼び出しコードと組み合わせた実際のクラッシュ再現は行っていない。**新しい実験の実行が禁止されているため、本レポートでは実施していない**）。
3. `restricted_direction1()`（未使用の代替実装）にも同一の構造的パターン（早期リターン文の型不一致）が存在するが、こちらは現在の学習経路では呼び出されていないため、実害はないと考えられる（`agent.py`では`restricted_direction`のみが使用されている）。

### 3.4 Proposal Ver.2で修正候補となる事項（未実装、候補としてのみ提示）

1. **`denom_safe`の非対称性の修正**：`torch.sign(denom)*eps+eps`という式を、例えば`torch.where(denom>=0, eps, -eps)`のように、正負どちらの場合も確実に`|denom_safe|≥eps`となる形に変更する候補。
2. **早期リターン文の戻り値の型統一**：`return W2_use.clone()`等の単一テンソルを返す箇所を、`return W2_use.clone(), 0.0`（または適切な`m_dir`の代替値）のようにタプルへ統一する候補。
3. **`m1`,`m2`自体へのisfiniteチェックの追加**：現状は`w_dir`まで計算が進んでから初めて非有限性がチェックされるが、`m1`,`m2`が計算された直後にチェックすることで、問題の発生箇所をより早期に特定できる可能性がある。

**これらはいずれも修正の候補として提示するのみであり、本レポートでは実装していない。**

## 4. 総括——過度に重大視しないための整理

- **本レポートで発見した問題は、コード上に存在する潜在的な脆弱性ではあるが、これまでに実施された全ての実測（106 run）では一度も顕在化していない。** これは、この問題を引き起こす条件（`denom1`または`denom2`が幅`eps=1e-8`というきわめて狭い区間に入ること）が、少なくとも現在の実験設定（Pendulum-v1、現行ハイパーパラメータ）のもとでは、発生確率が低いことを示唆する。
- **`denom_safe`の非対称性自体（正の小さい値は`2eps`、負の小さい値は`0`になるという設計）は、意図的な設計というより、`sign(x)*eps+eps`という式が`x`の符号に応じて異なる結果を生む副作用である可能性が高い**（`sign(0)=0`の場合に`eps`という安全な値を返すことを意図した式が、負の小さい値に対しては偶然`0`を返してしまう、という理解が自然である。ただし、この式の設計意図そのものはコード上のコメントからは確認できず、断定はしない）。
- **本レポートで新たに発見した「早期リターン文の戻り値の型不一致」は、`denom_safe`の問題とは独立した、より広範な（`restricted_direction()`内の複数の早期リターン文に共通する）構造的な特徴である。** これも、対応する分岐が一度もトリガーされていないため、これまでの実験結果には一切影響していない。
- **したがって、現時点でのProposal Ver.1の100-run本番結果・診断結果の正当性は、本レポートの発見によって損なわれない。** 本レポートは、将来的な実験条件の変更（より長い学習、異なる環境、異なるハイパーパラメータ等）において、この潜在的な脆弱性が顕在化する可能性を事前に把握するための調査である。
